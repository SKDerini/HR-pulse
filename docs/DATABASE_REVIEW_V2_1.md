# Анализ базы данных для версии 2.1

## Вывод

Текущая модель `app.hr_records` подходит для этапа активного уточнения требований: основные поля вынесены в индексируемые колонки, а изменяемая бизнес-структура хранится в `jsonb`. Полностью переделывать базу под отдельную таблицу для каждого экрана сейчас не требуется.

Для офферов нельзя использовать одну широкую строку со столбцами «бонус 1», «порог 1», «процент 1» и так далее. В исходном Excel встречаются разные модели: процент от прибыли или оборота, ступени выполнения плана, фиксированные бонусы, квартальные KPI и суточные. Новая схема хранит их единообразно как набор условий внутри версии мотивации.

## Сущности

| Сущность | Назначение | Ключ | Изменяемость |
|---|---|---|---|
| `offers` | Текущая карточка оффера | `offerId` | Изменяется HR/HRD |
| `offer_motivation_versions` | Снимок условий мотивации | `versionId` | После создания неизменяем |
| `offer_events` | Аудит изменений карточки | `eventId` | Только добавление из приложения |

Карточка оффера содержит ФИО, необязательную связь с Employee ID, подразделение, должность, сумму, валюту, дату, статус и `currentMotivationVersionId`.

Версия мотивации содержит номер, название, оклад, дату начала, причину изменения, автора, дату создания и массив `items`. Каждый элемент массива имеет поля: блок, показатель, условие, вознаграждение, период и комментарий.

## Что усилено в PostgreSQL

- частичные индексы по дате оффера, Employee ID и версиям конкретного оффера;
- уникальность пары `offerId + versionNumber`;
- проверка обязательных полей и неотрицательной суммы;
- проверка, что версия относится к существующему офферу и имеет хотя бы одно условие;
- запрет изменения и удаления сохраненной версии мотивации;
- запрет чтения офферов руководителем и табельщиком на серверном уровне.

## Почему сохранена гибридная модель

Она позволяет добавлять новые поля формы без рискованной миграции всех прежних данных. При этом самые частые фильтры табеля и офферов используют обычные индексы PostgreSQL, поэтому чтение не требует полного просмотра `jsonb`.

## Когда нужна следующая миграция

- При нескольких миллионах дневных записей табеля — вынести `timesheet_entries` в секционированную таблицу по году.
- При необходимости строить массовую аналитику по отдельным KPI — вынести элементы мотивации в дочернюю таблицу, сохранив версионность.
- При интеграции с бухгалтерией — добавить неизменяемый идентификатор сотрудника во внешней системе; ФИО оставить только отображаемым полем.

Эти изменения можно выполнить позже через адаптер данных без полной переделки веб-интерфейса.
