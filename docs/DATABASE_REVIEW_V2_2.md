# Анализ базы данных для версии 2.2

## Вывод

Текущая модель `app.hr_records` подходит для импорта сотрудников без перестройки рабочей базы. Основные ключи остаются индексируемыми колонками, а поля карточки и сведения об импорте хранятся в `jsonb`.

Импорт не должен напрямую заменять весь реестр одним файлом. Безопасный процесс состоит из разбора файла, сопоставления колонок, сверки с базой, предварительного просмотра и подтвержденной пакетной записи. Отсутствие сотрудника в файле не считается увольнением.

## Сущности импорта

| Сущность | Назначение | Ключ | Доступ |
|---|---|---|---|
| `employees` | Актуальные и уволенные сотрудники | `employeeId` | По действующим ролевым правилам |
| `employee_imports` | Заголовок загрузки и итоговые счетчики | `importId` | Только HR/HRD |
| `employee_import_rows` | Построчный аудит изменений | `rowId` | Только HR/HRD |

Сам Excel/CSV не сохраняется в базе. В журнал попадают имя файла, лист, автор, время, сопоставление колонок, результат каждой выбранной строки и перечень измененных полей.

## Правила сопоставления

1. Точное совпадение `employeeId`.
2. Уникальный табельный номер.
3. Уникальное нормализованное ФИО.

Дубли идентификаторов, неоднозначные ФИО и попытка автоматически вернуть уволенного сотрудника в действующие блокируются. Пустые значения не перезаписывают заполненные поля. Статус «Уволен» определяется по дате увольнения или явному статусу.

## Производительность

Запись выполняется пакетами по 500 сотрудников через существующий RPC `api.hr_records_bulk_upsert`. Для истории загрузок добавлены частичные индексы по дате импорта и паре `importId + employee_id`. Для нескольких сотен или нескольких тысяч сотрудников этого достаточно с запасом.

Если число сотрудников вырастет до десятков тысяч и импорты станут ежедневными, журнал строк можно вынести в отдельную нормализованную таблицу без изменения веб-интерфейса.
