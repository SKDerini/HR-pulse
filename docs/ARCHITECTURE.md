# Архитектура HR Строяков 2.1

## Компоненты

```text
Браузер
├─ единый интерфейс: 3 активных и 9 отключенных модулей
├─ бизнес-логика и расчеты
├─ импорт/экспорт Excel
└─ адаптер данных
   ├─ Preview: IndexedDB
   └─ Production: Layero Data API
                       │
                       ▼
                 PostgreSQL Layero
                 ├─ app.hr_records (рабочие сущности)
                 ├─ app.hr_user_roles
                 ├─ app.validate_hr_record (контроль целостности)
                 └─ api.hr_* RPC
```

Публичный ключ Data API находится во фронтенде — это штатная модель Layero. Сам ключ не открывает данные. Доступ определяют сессия пользователя и серверные функции из SQL-миграции.

## Хранение данных

В PostgreSQL используется универсальный реестр `app.hr_records`. Индексируемые поля (`entity`, `record_id`, `employee_id`, `manager_id`, `department`, `period`, `record_date`, `email`) вынесены в отдельные колонки, а расширяемая часть записи хранится в `jsonb`.

Такой вариант позволяет добавлять поля в карточки без полной перестройки базы, но сохраняет быстрые фильтры по сотруднику, периоду и подразделению. Для крупного табеля созданы отдельные индексы по `entity + period` и `entity + employee_id`.

Для офферов используются три логические сущности:

- `offers` — единственная текущая карточка оффера и указатель на актуальную мотивацию;
- `offer_motivation_versions` — неизменяемые снимки условий мотивации;
- `offer_events` — аудит изменений суммы, статуса, подразделения, должности и активной версии.

Сложная мотивация хранится в версии как массив условий `items`: блок, показатель, условие/порог, вознаграждение, период и комментарий. Это покрывает проценты от прибыли или оборота, ступенчатые пороги, фиксированные бонусы, квартальные KPI и суточные без добавления новых столбцов при каждой новой схеме.

SQL-триггер проверяет обязательные поля оффера, неотрицательную сумму, наличие условий и связь версии с оффером. Историческую версию нельзя изменить или удалить. Частичные индексы ускоряют выборку офферов по дате и сотруднику, а версий — по офферу и номеру; пара `offerId + versionNumber` уникальна.

## Доступ

- **HRD** — HR Pulse, реестр офферов, полный табель и управление правилами доступа.
- **HR** — HR Pulse, реестр офферов и полный табель.
- **Руководитель** — HR Pulse и табель только по дереву собственных подчиненных.
- **Табельщик** — HR Pulse и табель только по сотрудникам, разрешенным правилами.

Суммы и мотивация офферов доступны только HR и HRD. Это ограничение проверяется в клиентской бизнес-логике и в SQL-функции видимости; руководитель или табельщик не получит эти записи через прямой вызов Data API.

Правила табеля поддерживают подразделение, прямых подчиненных, всю иерархию и выбранные Employee ID. Проверка выполняется и в интерфейсе, и в SQL-функциях записи.

Таблицы схемы `app` не выдаются браузеру. Чтение и запись проходят через функции `api.hr_query`, `api.hr_record_upsert` и `api.hr_records_bulk_upsert`.

## Предпросмотр

IndexedDB повторяет тот же контракт операций. Реестр офферов, история мотивации, табель и экспорт Excel работают так же, как в рабочем режиме. Локальная база относится только к конкретному браузерному профилю и не синхронизируется между компьютерами.

## Масштабирование

Для текущего масштаба до нескольких сотен сотрудников универсальный реестр с индексируемыми колонками подходит с запасом и позволяет быстро менять формы. В отличие от Google Sheets, PostgreSQL не требует ежегодно разносить табель по отдельным документам.

При росте до миллионов дневных записей рекомендуется без изменения интерфейса вынести `timesheet_entries` в секционированную по году таблицу. Если по мотивации появится массовая аналитика отдельных KPI, массив `items` можно нормализовать в дочернюю таблицу. На текущем этапе это усложнило бы ввод и миграцию без заметной пользы, поэтому выбрана гибридная модель: типовые ключи индексируются, вариативные условия остаются в `jsonb`.
